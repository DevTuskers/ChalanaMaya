# Documentation

These documents describe ChalanaMaya's behaviour. The P0 MVP and the P1 phase are implemented with React, strict TypeScript, Vite, HTML Canvas 2D, roughjs, and perfect-freehand, served by a Node server (Express, SQLite via better-sqlite3); see the status table below. How to run the server and connect agents: [setup guide](agents/setup.md).

## Scope

In scope: a single-user whiteboard with drawing, styling, selection, canvas controls, local saving, and export. P0 features form the MVP; P1 and P2 remain planned work, not MVP promises. External embeds may need a network connection and permission from their providers.

Planned next (see the [agent canvas plan](plans/agent-canvas.md)): animated CSS component items and hardening (phase 6).

Out of scope: collaboration features (accounts, permissions, cursors, comments), hosted sharing services, encryption for shared sessions, libraries, built-in AI generation, and app-level extras listed in [out of scope](out-of-scope.md). Local file export is not a hosted sharing service. Simple draw-to-shape recognition is an explicit drawing feature, not a generative AI feature.

## Feature tracking

Each feature heading has a permanent ID: DRAW, STYLE, ARR, VIEW, FILE, SESS, AGENT, or MEDIA followed by a number. Never reuse or renumber an ID; mark retired features as retired. Descriptions explain intent and acceptance bullets define completion.

- **P0**: MVP must-have.
- **P1**: soon after MVP.
- **P2**: later.

All features start as **planned**. Track implementation in issues using the feature ID, priority, and status (planned, in progress, done, or deferred). Link evidence for every acceptance bullet before marking done. Update these specs when an approved decision changes behaviour; do not treat a priority as proof of completion.

Agent canvas phase 5 (GIF and video elements): uploads accept GIF, MP4 and WebM besides pictures (magic bytes checked; 10 MB per picture or GIF, 25 MB per video via `MAX_VIDEO_BYTES`); the server reads a video's size and duration from its MP4 (`moov`/`tkhd`/`mvhd`) or WebM (EBML) header without decoding it (`server/media/videoMeta.ts`) and falls back to 480×270. Uploaded GIFs and videos are drawn on the board canvas in layer order (`src/render/media.ts`: GIF frames decoded with `ImageDecoder`, at most 400 frames, otherwise the first frame and a notice; one muted, looping `<video>` per item, at most 6 playing, released when off screen) and move, resize, rotate, crop, flip, group, layer, lock, undo, redo and sync like pictures; pause, loop and autoplay are stored on the item and synced, mute is per tab; the properties panel has Play/Pause, Restart, Mute and Loop. Links (`https` only; no IP addresses, `localhost`, single-word or private names; `src/shared/urls.ts`) are stored as remote files that the server never fetches (`POST /api/sessions/:id/links`, MCP `place_media` with `source: {url}`) and shown by the browser in a live HTML layer (`src/ui/LiveMedia.tsx`, pictures with `referrerpolicy="no-referrer"`, videos with the page's origin-only referrer policy, keeping their own proportions inside the item, at most 24 live items, only on screen and not when zoomed far out), with a placeholder card on the canvas until the live item has loaded and always in PNG and SVG exports; names ending in a dot and wildcard IP names such as `nip.io` are refused too; the eyedropper catches the `SecurityError` of a tainted canvas and samples a media-free redraw. PNG export shows a GIF's first frame and a video's frame with a play badge, drawn from the `<video>` already on the board (round 2: export no longer swaps in a `data:` copy, which the page CSP blocked, leaving a "Video" card in the export and a stalled video on the board). `.chalana` files are format version 2 (links kept as links; version 1 still opens). Files can be inserted from the menu, pasted or dropped; **Add media link…** adds a link. MCP `place_media` takes `kind: "image" | "gif" | "video"` and `{file_id}`, `{data_base64, mime_type}` or `{url}` (with a warning that links are live only), plus `autoplay`/`loop` for videos; `get_scene` reports mime, source, link, duration and playback. Smoothness (MEDIA-10): the animation loop runs at 30 fps only while a playing item is on screen, repaints only the playing items' rectangles, steps down to 15 and 10 fps when frames cost over 12 or 25 ms, and pauses moving media with a **Play** notice after 2 s over budget at 10 fps; on boards of 500 or more items a drag paints the moving items over a still layer, so a 1 s drag on a board with 2,000 shapes, 4 GIFs and 3 videos has no task over 50 ms; reduced motion starts media paused and follows the system setting live. Not yet: the play badge on paused items (MEDIA-03) and keeping videos of very large boards as links when saving (MEDIA-07). Agent canvas phase 3 (live sync between tabs): each board page opens a WebSocket to `/api/sessions/:id/socket` (same-origin only, `server/sync/socket.ts`). The client says `hello` with its `clientId` and the last revision it has (`sinceRev`); the server answers with the `changes` since then, or a full `snapshot` when that revision is no longer covered (or ahead of the board). Edits are sent as `push` messages with the same `pushId`/`baseRev`/ops as the REST `/ops` route and go through the same `SessionService.apply()` (so the same validation, limits, last-writer-wins per item, tombstones and `pushId` dedupe); the sender gets an `ack`, and every other socket on the board gets the `changes` (REST and import writes are broadcast too, so a write by an agent or another client shows up live). Pings keep the link alive; a dropped link reconnects with backoff (500 ms up to 10 s) and resumes from `sinceRev`, and REST stays the fallback for imports, keepalive on `pagehide` and whenever no socket is up. In the tab, remote changes are applied by `store.applyRemote()` (`src/store/store.ts`, `src/scene/rebase.ts`): items this tab has not touched take the remote version at once and keep the server's layer keys (Rule E), items with an edit not yet acknowledged keep the local edit until its push settles (Rule B), every remote change goes into a lazy `RemoteLog` so undo, redo, Esc-cancel and drag restores rebase onto other tabs' changes instead of reverting them (Rule C, undo is per tab), an echo of this tab's own write is not logged, and `finalizeScene` repairs connector ends and bound labels afterwards without sending derived-only fixes back and forth (Rule F; a label whose box was removed elsewhere stays as free text). A change to an item that another tab removed is refused with the notice "Someone removed that item, so your change was not kept." Pending pushes are mirrored per tab (`chalanamaya.pending.<id>.<tab>`, the tab id kept in `sessionStorage`; the phase-2 board-wide key is still read), so two tabs never clear each other's offline changes; a tab holds a lease on its id (`chalanamaya.tablive.<tab>` heartbeat plus a BroadcastChannel ping), so the mirror of a closed or crashed tab is adopted and replayed by the next page that opens the board, and a duplicated tab picks a new id. The remote log keeps the latest change per item (`src/sync/remoteLog.ts`), so undo never loses other tabs' items however much they changed. Every element from the server is checked with `validateStoredElement` before it is shown. The socket allows 50 sockets per board, 2,000 per server, 50 pushes per second and 10 hellos per 10 s per socket. The status shows Saved, Saving, "Saved · not live" (socket down, REST saving) or "Offline — your changes will be sent when the connection is back." Evidence: `server/sync/convergence.test.ts` (two tabs with different text measurers and a scripted agent against a real `SessionService` and sync core: the §8 script with Controller drags, Esc and undo over 100 seeds, geometric binding checks, agent items surviving undo; randomised two-tab convergence over 100 seeds by default, `SEEDS`/`STEPS` to run more; Rules B, C, E and F, undo isolation, tombstones, layer order, a 1,000-item drag, own-write echoes), `server/socket.test.ts` (a real server and sockets: snapshot and `sinceRev` resume, snapshot fallback, ack and broadcast to every other socket only, duplicate `pushId`, REST broadcast, tombstones, malformed messages, refused upgrades, ping), `src/sync/sync.test.ts` (per-tab mirrors, leases, orphan adoption), `src/sync/remoteLog.test.ts` (latest-per-id equals full replay, timing), `server/sync/core.test.ts` (socket caps, hello limit), `e2e/sync.spec.ts` (two pages within 1 s, layer order both ways, simultaneous edits kept, undo isolation, a 1,000-item drag, offline edits after reconnect, a REST write shown live).

Agent canvas phase 2 (server-backed sessions in one tab): `/` creates a board and replaces the address with `/s/<id>` (24 URL-safe characters); `/s/<id>` replays any pending changes kept in this browser, loads the board from `GET /api/sessions/:id/scene` and saves through `POST /api/sessions/:id/ops` (`src/sync/`). Saves are throttled (the first change starts a 250 ms timer, so a long drag is saved at least every 250 ms, and a committed step is saved at once), diffed against what the server holds into `put`/`del`/`settings` ops with fractional layer keys, split into pushes of at most 500 ops and 1.5 MB, and sent one at a time; an item the server would refuse (over 256 KB or invalid) is refused locally and put back with a notice. Every push is mirrored in `localStorage` (`chalanamaya.pending.<id>`, at most 2 MB, compacted to the newest op per item) with its original `pushId` and `baseRev` before it is sent, plus the ops not yet sent; on `pagehide` a batch of at most 60 KB goes out with `fetch(..., { keepalive: true })`. A reload replays mirrored pushes in order with `mirrored: true` (the server dedupes them by `pushId`, or checks item versions once the push log has been trimmed, so a replay never overwrites newer edits) and re-sends the unsent ops. Replay never blocks opening the board: if the server is unreachable, rate-limited or failing, the board opens from `/scene` with the pending batches drawn on top, and they are re-sent later with their original `pushId` and `baseRev`. Replayed batches are cleared from the mirror once acknowledged; changes the server ignored as stale or rejected give the notice "Some changes from your last visit were not kept…". Reorder hints (bring to front/back) are kept in undo history, so undo and redo send the same layer moves. The save status shows Saved, Saving, Not saved — offline, board deleted, or server storage full. Pictures are uploaded to `/api/sessions/:id/files` and referenced by URL; copy and paste of pictures works within a board and between boards (a picture pasted from another board is uploaded again into the new board's files). Only `data:` URLs and same-origin `/api/sessions/<id>/files/<fileId>` paths are ever drawn or fetched, so imported files cannot make the page load other addresses or taint the canvas; `.chalana` saves and PNG/SVG exports still embed them. Opening a `.chalana` file and importing the board kept by the earlier browser-only version (`chalanamaya.board.v1`, offered in a banner and in the menu) both canonicalise, upload pictures and send one atomic `/import`, recorded as one local undo step (an import refused as too large leaves no empty undo step); the old browser copy is kept until **Remove the old copy**. Rule D: session files are add-only and undo/redo keep the current files. The main menu's board section has the title, the short id, **New board** (a link, so Ctrl/⌘ + click opens a new tab), **Copy board link**, **Copy board id**, up to 20 **Recent boards** kept in this browser, and the access warning. Board colour and grid are saved with the board; theme, zoom and scroll stay in the browser. An unknown id shows a "does not exist" page with **Start a new board**; a malformed address (`/s/not-a-board`, `/s/<id>/extra`) gets the same page with HTTP 404 and never creates a board. The legacy banner's dismiss button is **Hide this** (the old board stays available from the menu). Evidence: `src/sync/sync.test.ts` (chunking, refusal, mirror compaction, exact sizing and quota, replay including retryable failures and stale notices, throttling, diffing, keepalive with an in-flight batch, connectors, reorder history, picture clipboard and URL guards, Rule D, recent boards), `server/sync.test.ts` (the sync client against a real server: a 1,000-item move in chunks, a 5 MB import as one revision and one undo step, replay against newer edits and after the push log is trimmed, import dedupe, push-log eviction at 2,000 rows), `e2e/sessions.spec.ts`, `e2e/server.spec.ts`.

Known limits: live sync keeps the latest change per item (two tabs editing one item at the same moment do not merge inside it; the later one wins); there are no cursors or presence. A server restart drops the sockets, and tabs reconnect on their own. Pictures are kept by the server; adding a picture while the server cannot be reached is refused. Right-aligned auto-width text grows leftwards from the click point by design. Connector labels sit on a patch of the board colour, which also hides grid lines behind the label.
